Extracting Clause Structure from Legal Contracts

A recommended pipeline for turning 50-page PDF contracts into reliable, hierarchy-aware structured data.

The short version

A 50-page legal contract is absolutely manageable — but not by “OCR the PDF and ask an AI to find the clauses.” That approach produces exactly the problems described. The reliable solution is a two-stage, document-structure pipeline with a deterministic layer in the middle.

PDF  →  layout-aware parsing  →  deterministic section reconstruction
→  LLM clause classification  →  validation

Part 1

The recommended approach

Clause numbering is a tree, not text

Something like this:

Section 2. Indemnification
(a) Seller shall…
    (i)  …
    (ii) …
(b) Buyer shall…

…isn’t merely text — it’s a tree structure. The system needs to understand that (i) belongs to 2(a), not simply that (i) appears somewhere after Section 2.

What I’d use for the parsing layer

First choice would be Azure Document Intelligence Layout, Google Document AI Layout Parser, or AWS Textract Layout.

  • Azure — explicitly extracts paragraphs, headings, sections, tables, lines, and positional information. It can also emit structured Markdown, which is particularly useful before handing the contract to an LLM.
  • Google Document AI Layout Parser — purpose-built to turn complex documents into structured, machine-readable blocks/chunks while retaining layout.
  • AWS Textract — identifies titles, headers, paragraphs, lists, section headers, page numbers, tables, and their bounding boxes.

Given existing AWS development, Textract is reasonable — but benchmark it against Azure Document Intelligence on 10–20 representative contracts before committing.

The single biggest change

Don’t let the LLM determine the numbering. This is probably the most important departure from the current approach.

Suppose parsing gives you:

SECTION 2. REPRESENTATIONS

(a) Organization. The Company is…
(b) Authorization. The Company has…
    (i)  execution of this Agreement…
    (ii) performance of its obligations…

SECTION 3. COVENANTS

Don’t simply prompt “extract all clauses and tell me their section numbers.” Instead, write a small parser that recognizes numbering patterns: 

ARTICLE IV     Section 4.2     (a)
Article 4      4.2             (i)
SECTION 4      4.2(a)          (A)
                               (1)

Then construct an internal tree:

{
  "article": "ARTICLE IV",
  "sections": [
    {
      "number": "4.2",
      "title": "Representations and Warranties",
      "subsections": [
        {
          "number": "4.2(a)",
          "title": "Organization",
          "children": [
            { "number": "4.2(a)(i)", "text": "…" }
          ]
        }
      ]
    }
  ]
}

That is far more reliable than asking an LLM to infer hierarchy across 50 pages at once.

Then use the LLM for what LLMs are good at

Once the structural tree exists, send individual sections (or small groups) to the model and ask it to classify them: 

{
  "clause_id":       "4.2(a)",
  "heading":         "Indemnification",
  "clause_type":     "indemnification",
  "text":            "…",
  "page_start":      17,
  "page_end":        18,
  "parent_section":  "4.2",
  "confidence":      …
}

A starting taxonomy:

IndemnificationLimitation of LiabilityTerminationConfidentialityGoverning LawAssignmentChange of ControlForce MajeureInsuranceRepresentations & WarrantiesCovenantsPayment TermsIntellectual PropertyNon-competeNon-solicitationDispute ResolutionArbitrationNoticeDefinitionsRenewalAudit RightsData Protection

The model should classify existing sections, not rewrite the contract structure.

Preserve coordinates and page numbers

Never throw away the OCR metadata. Each extracted block should retain something like: 

{
  "page":            17,
  "bounding_box":    […],
  "text":            "…",
  "ocr_confidence":  0.997,
  "block_type":      "paragraph"
}

Textract returns location geometry and confidence for detected elements. That lets the final application show:

Indemnification — §8.3(b)
Pages 27–28

…and when someone clicks it, display the exact source portion of the PDF. That source traceability is especially important for a legal-document system.

Don’t OCR PDFs unnecessarily

Before running OCR, check whether the PDF already has a text layer. Many contracts that look like scans are actually digitally generated PDFs. In those cases: 

PDF text extraction → layout reconstruction     ✓ preferred
PDF → image → OCR → text                       × introduces errors

Only OCR scanned/image pages. You can mix modes per page:

                        ┌─ Native text → extract directly
PDF → inspect each page ┤
                        └─ Image page  → OCR

The validation layer

This is what takes the system close to production/legal-review quality. If the parser sees 2(a), 2(b), 2(d) it should flag “Possible missing subsection: 2(c)” instead of silently proceeding. Likewise 3.1, 3.2, 3.2, 3.4 should generate a duplicate/missing-number warning.

Why the current approach has been struggling

Currently OCR → LLM → clause JSON
Instead Layout extraction → hierarchy parser → LLM → validator

The deterministic middle layer makes an enormous difference. And don’t process all 50 pages as one giant LLM request — the document hierarchy gives you natural chunk boundaries. (Azure itself uses layout-aware semantic chunking based on paragraphs and tables for retrieval scenarios.)

Suggested stack

  • Python or TypeScript
  • Azure Document Intelligence or AWS Textract
  • A regex / state-machine section parser
  • LLM structured-JSON extraction
  • PostgreSQL JSONB

With a data model roughly:

document → page → article → section → subsection → clause

…retaining page_number, bounding_box, raw_text, normalized_text, and parent_id at every level.

The state-machine/section parser is probably only a few hundred lines of carefully written code — and that component, rather than a more powerful OCR model or a bigger LLM, is likely what solves the “Paragraph 2 Section (a)” problem.

Part 2 — Follow-up question

Amazon Textract or Docling for OCR and layout extraction?

Between the two, I’d usually choose Textract for production OCR/layout extraction and Docling for post-processing / structure normalization — rather than treating them as direct substitutes.

Amazon Textract
Stronger as the OCR engine for scanned legal contracts. Returns words, lines, tables, forms, geometry/bounding boxes, and layout elements with confidence scores. 		Docling
Very useful for turning PDFs into a cleaner structured representation — headings, paragraphs, tables, reading order, Markdown/JSON. Its OCR path depends on the backend you configure, so it’s not what I’d trust most for difficult scans.

For preserving Section 2 → (a) → (i) → (A), I’d use: 

Textract → Docling/custom normalization
         → deterministic hierarchy parser → LLM clause classifier

If the PDFs are mostly born-digital rather than scanned, test Docling first — avoiding OCR when a reliable text layer exists is preferable. For mixed or scanned PDFs, Textract becomes much more attractive.

The key point: neither tool alone will perfectly reconstruct legal numbering hierarchy. I’d still build a state machine around the extracted blocks, using indentation, numbering patterns, font/layout cues, page coordinates, and reading order. That’s where reliable 2(a)(iii) labeling comes from.

Part 3 — Follow-up question

Can PDFs that aren’t images be extracted with a PDF reader?

Yes. If the PDF isn’t scanned and contains an embedded text layer, you generally should extract the text directly rather than OCR it. There are three situations:

Born-digital Created from Word, a CLM system, etc. Text is embedded. PyMuPDF, pdfplumber, or pypdf can extract it directly — no OCR errors, and much faster.
Scanned / image Each page is essentially a photograph. A normal PDF parser won’t recover the words, so OCR (e.g. Textract) is required.
Hybrid Some pages have real text, others are images. The pipeline should detect this page-by-page and OCR only what needs it.

So I’d design the ingestion path like this:

PDF → detect usable text layer
    → direct PDF extraction when available
    → OCR fallback when needed
    → layout/hierarchy reconstruction
    → clause extraction

One caveat: even with a born-digital PDF, plain text extraction doesn’t automatically solve the hierarchy problem. You might get: 

2. Indemnification (a) Seller… (i) …

…while losing indentation, font size, coordinates, and reading order. So favor a PDF extraction library that preserves bounding boxes and layout, not one that returns a single giant string. For Python, PyMuPDF (fitz) is high on my list — it gives words/blocks with coordinates, which is exactly what you need to reconstruct Section 2 → (a) → (i).

Bottom line: don’t send every PDF through Textract. First determine whether you can reliably extract native text and layout; Textract becomes the fallback for the pages where you can’t.
